# 人工智能责任包治理入口

本目录规定怎样新建、修正、扩展、整改或审计由人工智能执行的Module、Template、Feature，以及会改变其输入或确定性消费方式的Cover等同类正式责任包。它治理维护方法，不取得被维护包的业务创作权，也不建立Workflow路线或剧集生产授权。

模型直接读取的入口、规则、上下文和例子，以及会改变模型输入、必交结果或后续消费方式的清单角色、Schema、Validator、程序和直接消费者，都属于责任包修改面。

与人工智能输入、产物、接纳和消费者无关的纯确定性维护、没有人工智能创作流程且不改变上述链路的Visual／Cover和普通剧集生产不进入本规则。

小改仍须确认真实影响；符合[验证标准的纯说明修正条件](verification.md#任务级前向证据)时，只按目标文本、链接、直接真源和差异核对，不默认扩展到无关标准或完整运行链。受保护资源的消费者审计与具体授权不因此豁免，也不得借一次维护批量改写未触及的旧包。

## 先建立现场

任何写入前先确认：

- 目标包身份、真实人工智能入口和模型角色；
- 本次要改变的结果，以及第一个实际消费它的动作、程序或责任方；
- 当前Git差异、用户授权和活动工作单；历史查阅仅按[变更理由档案](../../AGENTS.md#变更理由档案)的条件与时间范围按需进行；
- 目标是边界内维护，还是改变身份、责任、Workflow、公共合同、失效或授权边界的架构变化。

身份、入口、消费者或影响范围不能从现场证明时，按下文共同停止边界处理；不用旧案例、推荐值或历史结论代替。

## 责任分工判断

项目新增、维护、修正和审计都先结合实际入口与消费者确认：哪些结果需要AI理解语义、取舍或专业判断，哪些可由程序根据已定输入计算和执行；是否存在程序冒充专业裁决、AI转抄或重复计算，以及交接缺少输入、结果、接纳者或失败去向。判据见[内部能力标准](internal-capability-standard.md#ai判断与程序执行)。

把判断直接落实到本次实现；需要建档时在同一变更记录说明，是否建档统一按[变更理由档案](../../AGENTS.md#变更理由档案)判断；没有行为变化的纯说明修正只核对对应文本与真源。

纯确定性变更只适用本段和相关判据，不因此要求AI包身份、模型复核或全套治理文件。

已有授权覆盖具体能力与目标时持续完成；只暂停真正依赖未决问题的操作。不得为这项判断新增打分、检查表、审批、模型调用或例行审计节点。

## 按任务读取

| 任务 | 读取 |
|---|---|
| 新建、删除、改名、移动责任包，或修改跨层结构、装配、入口、清单投递、模型上下文、根执行契约、跨阶段消费者 | [责任包标准](package-standard.md) |
| 修改内部步骤、候选、工作文件、分支、恢复、硬门或渐进披露 | [内部流程标准](workflow-standard.md) |
| 新建、维护、移动、删除方法、确定性资源、包内组件，或判断是否升级为正式包 | [内部能力标准](internal-capability-standard.md) |
| 修改已经使用的能力、共享消费者或受保护路径 | [能力保护标准](capability-protection.md)；涉及全画幅、讲解模板及其相关消费者时，先核对[专项设计基线](template-capability-protection.md#全画幅与讲解模板的设计基线) |
| 任何写入前确定验证范围，以及完成后判断证据是否充分 | [验证标准](verification.md) |
| 需要理解复杂步骤、联合创作、包内组件或真实渐进披露怎样同时成立 | 先读相关标准，再按需读[全画幅经典案例](examples/fullframe-narrative.md) |
| 需要审计Workflow节点、装配型Module、Template、Feature与迭代单位怎样形成一条执行路线 | 先读责任包与内部流程标准，再按需读[Author装配案例](examples/author-beat-assembly.md) |

同一任务命中多个主题时只读相关文件；不得为了少读一份规则绕过真实影响。

案例只解释规则怎样落到一个真实责任包，不是第二套标准。案例与现行包、清单、程序或消费者冲突时，以现场为准并修正或替换案例。

## 发起方式

用户明确指定整改对象、目标并要求实施，即授权维护者先只读核对并说明实际文件和影响，再在该范围内完成最小必要改动，不需要第二次确认。只要求审计、方案、讨论或明确要求先审阅建议时，不产生实施授权。

受保护能力还必须满足[能力保护标准](capability-protection.md#修改前的消费者审计与授权)的能力特定授权；相邻维护、笼统要求或机械放行不能把范围扩大到用户未明确授权的受保护能力。

涉及架构变化时，按`AGENTS.md`核对已有批准是否覆盖具体目标结构与范围；已覆盖则执行，未覆盖则先提交具体方案并暂停相关写入。扩大到未授权对象或改变已批准目标时，另行申请批准。

## Skill工程边界

人工智能Module的Skill工程先按本目录确认包身份、消费者和项目责任，再按当前宿主的Skill规范维护，保留项目包身份与现有结构。当前用户协作指令另有指定的Skill工程规则时，先完整读取其明确指向的文件；仓库不假定维护者的个人主目录，也不复制个人规则作为第二真源。

Template／Feature的`AUTHOR.md`、确定性程序、Visual和Cover按项目责任包规则维护。通用Skill工程不得接管本项目的包清单、消费者、架构或授权判断，也不得自动带入报告、评测、遥测、适配器或额外清单。

## 共同停止边界

必需输入缺失、正式状态不能证明当前模式、具体授权不存在、远端结果未知、活动工作单与共享维护冲突、包身份或消费者不明、跨阶段影响无法逐项证明时，暂停依赖该条件的写入或外部动作并报告具体阻塞；继续已授权且不依赖该条件的调查与方案准备。

现有材料仍不能解决时，只询问解除该阻塞所需的信息或授权。当前责任内的问题留在当前责任方修正；确属上游的问题返回真实上游。不得猜测输入、绕过批准、静默重跑、重投、付费、发布、扩大写入或新建第二条流程。

本规则不授权Git提交、剧集生产、付费、发布或远端重试；这些仍服从`AGENTS.md`。
